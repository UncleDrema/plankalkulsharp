# Машина Plankalkül

Машина — Windows-монитор над существующим компилятором и CLR. Она открывает исходники `.pk`, собирает их через Python-компилятор и запускает каждый модуль в отдельном .NET Worker. Отдельный набор виртуальных инструкций не вводится.

## Запуск и работа

```powershell
uv sync
uv run plankalkulsharp machine examples/reverse_list.pk
```

1. Откройте `.pk`, задайте аргументы `5 3` и размер кучи. По умолчанию доступен 1 МиБ.
2. Нажмите «Запустить». Пример возвращает `2`; при корректном завершении все пять узлов освобождены.
3. Для наблюдения задайте задержку контрольных точек, например 100 мс, и запустите новый экземпляр.
4. Нажмите «Пауза». После подтверждения исполнителя можно выбрать объект на карте или в таблице и просмотреть его поля. Переход по ссылке выбирает связанный объект.
5. «Продолжить» возобновляет выполнение, «Остановить» завершает выбранный запуск.

Исходник в окне доступен только для чтения. Редактировать его можно внешним редактором; очередной запуск читает файл заново. У существующей записи сохраняется именно текст, переданный компилятору, поэтому позиция остановки не перемещается из-за последующих изменений файла.

### Рабочее окно

Слева находятся файлы и история запусков. Открытие `.pk` показывает соседние файлы из его папки; можно выбрать другую папку, отфильтровать имена или перейти к недавним файлам. Список из последних 20 путей сохраняется в пользовательских настройках, сами исходники не копируются. Поддерживаются перетаскивание одного `.pk`, Ctrl+O и команда «Файл → Перечитать файл». Для папки показывается только её непосредственное содержимое.

В центре код расположен рядом с нотацией. Разделители позволяют менять ширину панелей и высоту вывода. Флажок «Память» скрывает правую панель и освобождает место для программы; вкладка дампа остаётся доступной внизу. Выбор нижней вкладки сохраняется при запуске. F5 создаёт новый запуск открытой программы. В заголовке отмечено, когда отображается снимок существующего запуска.

«Стандартные планы» открывает каталог внутри того же окна, даже без загруженной программы. Доступны поиск по имени, описания, примеры и исходники шаблонов. Если текущая программа использует план, можно выбрать подстановку типов и увидеть его специализированную нотацию. Общий шаблон не запускается как самостоятельная программа. Каталог поступает из установленного Python-пакета через команду `plankalkulsharp library`, возвращающую JSON.

«Справка по языку» (F1) содержит поиск по заголовкам и тексту тем. Кнопка «Программа и нотация» возвращает к исходнику без потери состояния. Выбор Python находится в меню «Настройки». Эти разделы не останавливают работающие программы; управление выбранным запуском остаётся доступным сверху.

Голубая подсветка показывает последнюю полученную позицию исполнения, жёлтая — следующий участок на подтверждённой паузе. Подсветка видна и без фокуса в исходнике; текст прокручивается к выбранному участку. Без задержки обновления приходят до пяти раз в секунду; с задержкой снимок создаётся на каждой контрольной точке. Медленный интерфейс может пропускать промежуточные снимки. Для наблюдения за ними увеличьте задержку исполнения.

Окно хранит историю до закрытия приложения. Несколько запусков могут работать одновременно; у каждого свои аргументы, куча, вывод и состояние. Отображаемые идентификаторы объектов имеют смысл только внутри соответствующего запуска.

При запуске через команду `machine` используется Python из текущего окружения. Для прямого запуска WPF доступен выбор интерпретатора с установленным пакетом `plankalkulsharp`. Компилятор, Worker и WPF не требуют расположения рядом с исходным репозиторием.

## Компоненты и сборка

| Компонент | Обязанности |
| --- | --- |
| Python-компилятор | ANTLR, AST, проверка типов, генерация IL и вызов .NET-сборки |
| Runtime | Неуправляемая куча, проверки ссылок, снимки и контрольные точки |
| Worker | Загрузка одного модуля, управление его жизненным циклом и каналом наблюдения |
| WPF | Список запусков, управление, исходник, вывод и отображение памяти |

Worker и Runtime собираются из ресурсов Python-пакета в пользовательский кеш. WPF собирается отдельно при первом запуске интерфейса. Ключ кеша включает исходные ресурсы, версию .NET SDK, ОС и архитектуру. `PLANKALKUL_CACHE_DIR` позволяет явно выбрать каталог кеша, например для проверок. Готовый результат публикуется атомарно; обычные повторные запуски используют готовый Worker.

Python также хранит выходные файлы программ в подкаталоге `modules` этого кеша. Ключ включает весь сгенерированный IL с хешем и путём исходника, содержимое Runtime DLL и ключ среды сборки. При совпадении готовые DLL и сопутствующие файлы копируются в запрошенный каталог без вызова `dotnet build`. Изменение исходника, генерируемого кода, Runtime или среды сборки создаёт новую запись; изменение аргументов и параметров исполнения — нет. Только успешная сборка публикуется в кеше. Удаление временного каталога запуска и закрытие окна не удаляют этот кеш.

При первой сборке `dotnet build` восстанавливает зависимости NuGet. Для сборок программ, Worker/Runtime и WPF компилятор передаёт `-p:NuGetAudit=false`: база уязвимостей не загружается, аудит пакетов не выполняется. Проверка сертификатов и подписей сохраняется. Загрузка отсутствующих пакетов по-прежнему может требовать сети. Повторное использование готового модуля не запускает восстановление заново.

Вывод `dotnet build` передаётся по мере поступления в stderr компилятора. Журнал доступен во вкладке «Диагностика», результат — во вкладке «Вывод». Выбранная нижняя вкладка при сборке, запуске и обновлениях сохраняется. В режиме `build --json` stdout по-прежнему содержит только итоговый JSON. При использовании кеша журнал сообщает о готовом модуле.

Каждая программа собирается как библиотека со ссылкой на готовую Runtime DLL. Ни исходники распределителя, ни его DLL не копируются в каталог программы. В каждом Worker библиотека создаёт собственное состояние кучи. Общая реализация системных операций не означает общей памяти между программами.

```powershell
# Только IL
uv run plankalkulsharp compile examples/reverse_list.pk -o build/list.il

# Сохранённый модуль: можно собрать исходник или новый библиотечный IL
uv run plankalkulsharp build build/list.il -o build/list --json

# Обычный запуск с временной сборкой
uv run plankalkulsharp run --memory-stats examples/reverse_list.pk -- 5 3
```

JSON-ответ `build` содержит `ok`, `artifact` с абсолютными `assemblyPath` и `workerPath`, `source` с путём, текстом и SHA-256 и `diagnostics`. При ошибке процесс возвращает 1. У диагностики есть этап, сообщение и, когда она достоверна, позиция: строки отсчитываются от 1, столбцы от 0. Сборочный вывод не смешивается с этим JSON.

Ручной запуск собранного модуля: `dotnet <workerPath> --module <assemblyPath> -- 5 3`. Программная DLL сама по себе не является исполняемым приложением. Старые DLL с самостоятельным `Main` необходимо пересобрать из исходника.

## Контракт модуля

ABI 1 определяет класс `PlankalkulProgram` с публичными статическими методами:

```text
void Execute(string[] args)
string GetMetadata()
```

`GetMetadata` возвращает константный JSON с `abi`, `compilerVersion`, `source` и `heapTypes`. Каждый тип кучи имеет идентификатор, имя, размер и описание разметки. Разметка содержит вид значения (`bit`, `int32`, `int64`, `ref`, `record`), размер, номера и смещения полей. Ссылки используют `targetTypeId`, поэтому рекурсивный тип имеет конечное описание. Это разметка нашей кучи, а не физическое представление CLR-структуры.

Worker проверяет контракт до выполнения программы. Он создаёт кучу, вызывает `Execute`, сохраняет состояние и в `finally` освобождает ресурсы. Модуль не вызывает инициализацию или уничтожение кучи. CLI и поле аргументов WPF принимают значения JSON, преобразуемые согласно типам параметров: скаляры 32/64 бит, списки и записи. Все результаты печатаются по одному на строку. Правила описаны в [спецификации списков](lists.md).

## Управление

Компилятор вставляет `Execution.Checkpoint(line, column)` перед операторами, при входе в функции и на границах повторения циклов. Проверка команд не зависит от обращений к памяти: бесконечный вычислительный цикл тоже можно остановить.

Пауза кооперативная: кнопка отправляет запрос, а статус «Пауза» появляется после остановки на контрольной точке. Подсвечивается следующий участок исходника. Во время работы отображается последняя полученная позиция. Задержка от 0 до 1000 мс задаётся в Runtime и может изменяться во время выполнения; по умолчанию она равна нулю. Ожидания реагируют на остановку.

Коды завершения: 0 — успех, 1 — ошибка, 130 — остановка пользователем. Сначала среда запрашивает управляемую остановку. Через две секунды без завершения процесс принудительно прекращается. При закрытии окна останавливаются его программы; потеря канала также не должна оставлять Worker бесконечно работать в фоне.

Системные аварии и принудительное завершение не гарантируют выполнения `finally`. В этом случае память процесса возвращает ОС, а интерфейс располагает только последним полученным снимком.

## Канал наблюдения

WPF создаёт локальный именованный канал для конкретного запуска, Worker подключается как клиент. Сообщения — JSON по одной строке, UTF-8. Версия протокола — 1.

Команды содержат `version` и `command`:

| Команда | Данные |
| --- | --- |
| `start` | `heapSize`, `delayMs`, `arguments` |
| `pause`, `resume`, `stop` | без дополнительных данных |
| `delay` | `delayMs` |
| `inspect` | `handle` — строковое представление идентификатора объекта |
| `inspectHeap` | `offset` — смещение наблюдаемой страницы; на паузе возвращается до 256 байт, при выполнении страница поступает со снимками при задержке |

Ответы используют `event`: `state`, `snapshot`, `output`, `memory`, `inspection`, `diagnostic`, `completed`. События снимка содержат последовательный номер, время, позицию исходника и признак точности. Внутри `snapshot` находятся `stats`, `blocks`, `objects`. Идентификаторы объектов и значения полей передаются без преобразования в числа с плавающей точкой.

Без задержки снимки создаются не чаще пяти раз в секунду. При положительной задержке каждая контрольная точка создаёт снимок с текущей страницей дампа в поле `heapPage`; байты и метаданные объектов имеют одну ревизию и заменяются в очереди вместе. На паузе и перед уничтожением кучи передаётся точное состояние. Поток команд не читает неуправляемую память: снимки и инспекция обслуживаются потоком исполнения между законченными операциями распределителя.

Медленный интерфейс не должен останавливать программу. Промежуточные снимки заменяются более свежими, журнал памяти ограничен 5000 событиями, отображаемый вывод — 1 МиБ на поток. Усечение явно обозначается; итоговые состояния и диагностика сохраняются. Обычный консольный запуск не усекает stdout/stderr.

## Память и инспектор

Карта и таблица показывают смещения и размеры блоков, типы и места создания объектов. Статистика содержит число выделений и освобождений, занятые и свободные байты, пик, крупнейший свободный блок и число живых объектов. Показатели памяти процесса и процессорного времени выводятся отдельно: CLR, массивы, стек и служебные данные не входят в размер нашей кучи.

Инспектор запрашивает значения выбранного объекта на паузе и читает поля по проверенной разметке. Он не меняет программу, не выделяет объекты в её куче и не увеличивает счётчики распределителя. `NIL` и устаревшая ссылка отображаются как состояния ссылки; их просмотр не вызывает ошибку программы. Переход к живому объекту позволяет проследить цепочку `next`.

Вкладка «Куча (hex)» позволяет просматривать всю область по страницам из 256 байт, перейти к hex-смещению или открыть участок выбором блока на карте. В строке показаны смещение от начала кучи, 16 байт в hex и печатные ASCII-символы. Свободные байты отмечены `--`: их содержимое не читается, поскольку невыделенная системная память может быть неинициализированной. Выравнивающий хвост занятого блока входит в просмотр. Ответ `heapPage` содержит `offset`, полный размер кучи `size`, `snapshotSequence` и массив `bytes` (числа 0–255, `null` для свободного места). Чтение обслуживается потоком исполнения и не меняет счётчики. При задержке дамп обновляется на каждой контрольной точке перед ожиданием; на паузе и перед освобождением кучи приходит точный снимок. Без задержки во время работы сохраняется последняя прочитанная страница с отметкой об устаревании. Переключать страницу можно и при выполнении.

В hex-дампе байты объектов имеют мягкий цветной фон; выбранный в таблице объект выделяется золотистым. Выбор объекта задаёт его страницу, если она ещё не показана; нижняя вкладка при этом не переключается. Подсказка над байтами содержит ссылку, тип и диапазон объекта. Палитра повторяется; свободные байты и выравнивающий хвост за логическим размером объекта не окрашиваются. Принадлежность байтов сохраняется вместе со снимком, поэтому последующее переиспользование памяти не перекрашивает старые данные.

После продолжения ранее прочитанные поля считаются сохранённым снимком. После завершения остаются финальные метаданные и ранее полученные значения; новые чтения уничтоженной кучи невозможны. У принудительно завершённого запуска последний снимок явно помечается как неполный.

Алгоритм first-fit, разделение, слияние, выравнивание и проверки доступа описаны в [документе о динамической памяти](dynamic-memory.md).

## Ограничения

WPF-монитор предназначен для Windows. Проверка Linux/macOS не заявляется. Процесс Worker изолирует сбои программ от интерфейса, но не является песочницей для произвольного недоверенного IL.

Не добавлены редактирование исходника, LSP, пошаговый отладчик, локальные переменные и стек вызовов, изменение памяти из интерфейса, общая куча программ, планировщик виртуальных инструкций или новые конструкции языка. История запусков не сохраняется между открытиями приложения.
