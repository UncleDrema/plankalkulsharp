# Динамическая память и ссылки

## Нотация

`@T` в типе — типизированная ссылка на отдельный объект именованного типа `T`. В выражении `@T` выделяет нулевой объект, а `@` в компонентном пути разыменовывает ссылку.

```text
int = 32.0
node = (int, @node)

@node => Z0
7 => Z0[@.0]
NIL => Z0[@.1]
Z0 => Z1
Z0 => @
```

`NIL` совместим только со ссылочным типом. `expr => @` освобождает один объект; освобождение `NIL` ничего не делает. Присваивания, аргументы и результаты копируют идентификатор ссылки. Поэтому запись через одну копию видна через другую, а разыменование любой копии после освобождения ошибочно. Сами значения ссылок при освобождении не обнуляются; их копирование и сравнение не обращаются к памяти объекта.

Допустимы только `=` и `!=` между одинаковыми ссылочными типами: они сравнивают идентичность объекта. Числовые операции, порядок и преобразования между ссылками и числами не разрешены. Записи копируются по значению, включая поля-ссылки.

Типы имён регистрируются до разрешения определений, поэтому разрешены рекурсивные и взаимно-рекурсивные ссылки, например `node = (int, @node)`. Рекурсия по значению отклоняется. Прямая псевдонимизация сохраняет совместимость ссылок, но одинаковая структура двух самостоятельных имён её не создаёт.

## Куча и проверки времени выполнения

На запуск создаётся одна неуправляемая область. Её жизненным циклом управляет общий Worker, который загружает программный модуль; сама программа вызывает только операции памяти. Каждый Worker выполняет одну программу, поэтому кучи параллельных запусков изолированы. По умолчанию размер — 1 МиБ; `--heap-size` задаёт положительный размер в байтах, кратный 8, не больше `Int32.MaxValue`. Рантайм выделяет эту область через `NativeMemory.AlignedAlloc` и освобождает её через `AlignedFree`.

Распределитель ищет первый подходящий свободный блок в порядке адресов, делит его при необходимости и объединяет соседние блоки при освобождении. Каждый блок выровнен на восемь байт. Данные объектов находятся в неуправляемой области, а список блоков и таблица живых объектов — в служебных коллекциях C#.

Ссылкой служит положительный 64-битный идентификатор; `0` — `NIL`. Идентификатор не переиспользуется, даже если участок памяти получил новый объект. Поэтому старая ссылка не становится действительной после повторного использования блока. Выделение обнуляет блок. Ошибка нехватки памяти не меняет состояние распределителя.

| Данные | Размер и выравнивание |
| --- | --- |
| Бит | 1 байт |
| Последовательность 1–32 бита | 4 байта |
| Последовательность 33–64 бита | 8 байт |
| `@T` | 8 байт |
| Запись | поля с соответствующим выравниванием, итог округлён до 8 байт |

Куча принимает биты, последовательности до 64 бит, ссылки и записи из них. Массивы и записи с массивами пока не размещаются в ней. Рантайм проверяет существование объекта, ожидаемый тип и границы каждого чтения и записи. Сырые адреса не доступны программе.

## Алгоритм распределения

Worker передаёт `Heap.Initialize` конфигурацию запуска; вариант без аргументов читает прежние переменные окружения для консольного запуска и прямых проверок библиотеки. Инициализация резервирует служебную ёмкость для первого блока, затем выделяет выровненную неуправляемую область и добавляет в `Blocks` единственный свободный блок `[0, размер)`. Если создание служебных данных или самой области не удалось, уже выделенная область сразу освобождается. Повторный вызов инициализации при работающей куче ничего не меняет.

В рантайме есть две согласованные структуры:

- `Blocks` — список непрерывных участков в порядке возрастания `Offset`. Вместе они покрывают всю кучу без промежутков и пересечений. Каждый участок имеет положительный размер и помечен как свободный или занятый; соседние свободные участки после `Free` не остаются раздельными.
- `Live` — таблица `идентификатор → Allocation` для занятых объектов. Запись содержит смещение, логический `Size`, выровненный `ReservedSize`, идентификатор и имя типа, а также место выделения для отчёта.

`Size` — размер, вычисленный компилятором для значения: по нему проверяются обращения. `ReservedSize` — `Size`, округлённый вверх до 8 байт; именно такой участок занимает объект в `Blocks`, обнуляется и учитывается в использованной памяти. Например, для числа типа `32.0` значения равны `Size = 4` и `ReservedSize = 8`: чтение байта со смещением 4 запрещено, хотя резервированный хвост существует.

### Выделение

`Allocate` сначала убеждается, что куча запущена и запрошенный логический размер положителен, затем безопасно выравнивает его до восьми байт. Он последовательно просматривает `Blocks` и выбирает первый свободный участок, чей размер достаточен: это first-fit по адресу, а не поиск наименьшего подходящего участка.

До изменения списка и таблицы рантайм проверяет, что идентификаторы не исчерпаны, заранее увеличивает ёмкость `Blocks` и `Live`, создаёт запись выделения и, при необходимости, будущий свободный остаток. Ошибка подготовки метаданных оставляет распределение без изменений. Затем рантайм выдаёт следующий положительный идентификатор, обнуляет весь `ReservedSize`, помечает точный блок занятым либо вставляет за ним свободный остаток и добавляет объект в `Live`. Идентификатор никогда не выдаётся повторно; `0` всегда означает `NIL`. Благодаря этому ссылка на уже освобождённый объект не становится действительной, когда его прежний участок занимает другой объект.

### Освобождение и доступ

`Free(NIL)` немедленно завершается успешно. Для любой другой ссылки рантайм ищет её в `Live`, проверяет ожидаемый тип и находит соответствующий занятый блок по смещению. Он удаляет запись из `Live`, помечает блок свободным, затем сначала сливает его с левым свободным соседом, а после этого — с правым. Такой порядок восстанавливает инвариант одного свободного блока для каждого максимального свободного диапазона.

Любое чтение или запись проходит через ту же запись `Live`. После проверки ссылки и типа рантайм принимает доступ ширины `width` со смещением `offset` только при `offset >= 0`, `width >= 0` и `offset <= Size - width`. Вычитание в этой форме не допускает переполнения при проверке конца диапазона и не разрешает обращаться к выравнивающему хвосту. `NIL`, освобождённая ссылка, ссылка другого типа и выход за логические границы становятся диагностикой памяти.

При завершении `Heap.Shutdown` сначала печатает статистику, пока `Blocks` и `Live` ещё доступны, затем в `finally` освобождает неуправляемую область и очищает служебное состояние. Поэтому это выполняется и после обработанной ошибки программы.

В режиме монитора Worker перед очисткой также передаёт итоговый снимок. На паузе поток исполнения обрабатывает запросы инспектора: копирует значения полей по описанию типов, сформированному компилятором, без изменения кучи и счётчиков. UI не получает сырых адресов. При принудительном завершении процесса очистку его памяти выполняет ОС; последний полученный снимок не считается итоговым. Протокол наблюдения и управления описан в [устройстве машины](machine.md).

### Пример фрагментации

Исполняемый пример — [examples/fragmentation.pk](../examples/fragmentation.pk). Он выделяет блоки разных размеров и освобождает их не в порядке создания. Для наглядного просмотра откройте его в машине, задайте кучу **64 байта**, аргумент **0** и задержку **500 мс**. На паузе доступны карта блоков и вкладка «Куча (hex)».

```text
uv run plankalkulsharp machine examples/fragmentation.pk
uv run plankalkulsharp run --heap-size 64 --memory-trace examples/fragmentation.pk -- 0
```

Режим `0` показывает фрагментацию, объединение соседей, разделение и повторное использование первого подходящего блока. Результат — `0`, итог: 7 выделений, 7 освобождений, один свободный блок 64 байта.

Аргумент `1` намеренно запрашивает 24 байта при двух раздельных свободных участках по 16 байт. При куче **ровно 64 байта** программа завершится ошибкой (код `1`), хотя суммарно свободно 32 байта. Продолжения после ошибки нет; чтобы увидеть последующее объединение, запустите режим `0`. С кучей по умолчанию свободный хвост скроет этот отказ.

Ниже показано состояние кучи в 64 байта. Все четыре объекта имеют логический и резервированный размер 16 байт.

| Действие | `Blocks` по смещениям | Результат |
| --- | --- | --- |
| Выделить `A`, `B`, `C`, `D` | `A[0,16) B[16,32) C[32,48) D[48,64)` | Куча заполнена. |
| Освободить `B`, затем `D` | `A[0,16) free[16,32) C[32,48) free[48,64)` | Свободно 32 байта суммарно, но крупнейший участок — 16 байт. |
| Выделить объект размером 24 байта | без изменений | First-fit не находит непрерывный блок в 24 байта. |
| Освободить `C` | `A[0,16) free[16,64)` | `Free` объединяет `C` сначала с левым, потом с правым свободным блоком. |
| Выделить объект размером 24 байта | `A[0,16) E[16,40) free[40,64)` | Первый свободный блок подходит и разделяется. |

Слияние меняет только описания свободных участков. Живые объекты не перемещаются, поэтому распределитель не может объединить свободные диапазоны, между которыми остаётся занятый блок.

### Стоимость операций

Поиск первого блока при выделении и поиск блока при освобождении линейны по числу блоков `B`. `Blocks.Insert` и `Blocks.RemoveAt` сдвигают хвост списка, поэтому разделение и объединение также имеют стоимость до `O(B)`. `Live` — словарь: поиск и удаление имеют ожидаемую стоимость `O(1)`, добавление — амортизированную ожидаемую `O(1)` с учётом расширений таблицы. Вычисление `UsedBytes` для пика после каждого выделения проходит по всем живым объектам `L`, то есть добавляет `O(L)`. Обнуление выделенного участка занимает `O(ReservedSize)`. Статистика завершения отдельно линейно проходит по блокам и живым объектам.

## Ошибки и анализ

Разыменование `NIL`, обращение к освобождённому объекту, повторное освобождение, несовместимый тип и выход за границы завершают программу кодом `1` с диагностикой в stderr. При обработанной ошибке системная область всё равно освобождается.

Компилятор дополнительно обнаруживает однозначные обращения после освобождения и повторное освобождение через простые копии ссылок. После вызова функции, на границе цикла или слиянии ветвей состояние может быть неизвестно, и проверка выполняется рантаймом. Это не система владения и не заимствования Rust.

Неосвобождённые объекты не меняют код завершения, но показываются в статистике как живые объекты с местами создания. `--memory-stats` выводит число выделений и освобождений, занятые и свободные байты, пик использования, крупнейший свободный блок и оставшиеся объекты. `--memory-trace` также выводит выделения, освобождения, разделение и объединение блоков. Оба потока диагностики идут в stderr.

Для прямого запуска собранной DLL рантайм читает `PLANKALKUL_HEAP_SIZE`, `PLANKALKUL_MEMORY_STATS` и `PLANKALKUL_MEMORY_TRACE`. Размер задаётся в байтах, а флаги принимают `0` или `1`; трасса сама включает статистику. Обычный `run` выставляет эти переменные сам и не передаёт их программе как аргументы.

Фактический вывод для списка из одного узла с `--memory-trace` и кучей по умолчанию:

```text
memory: heap 1048576 bytes
memory: split 0: 16 + 1048560
memory: allocate #1 node 16 bytes at 0
memory: free #1 node 16 bytes at 0
memory: merge at 0: 1048576
0
memory: allocations=1 frees=1 used=0 free=1048576 peak=16 largest-free=1048576 live=0
```

Сгенерированный IL вызывает `PlankalkulRuntime`; при ручной сборке нужно использовать поставляемый `dotnet_assets/PlankalkulProgram.ilproj`, который подключает проект рантайма через `ProjectReference`.

## Границы

Нет ссылок на локальные переменные и отдельные поля, арифметики указателей, динамических массивов, сборщика мусора, владения, заимствований или многопоточности. Обычные массивы и записи сохраняют прежнее поведение.
