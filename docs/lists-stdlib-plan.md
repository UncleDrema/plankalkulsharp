# Единые списки и стандартные планы Plankalkül

Статус: реализация и автоматическая приёмка завершены 25 октября 2026 года. Визуальная проверка WPF передана пользователю; окно не запускалось.
Назначение: источник решений и порядка работы при продолжении задачи после сброса контекста.

## Согласованные решения

1. Переработать существующие массивы в единую модель однородных списков. Не создавать рядом независимый контейнер с почти такой же семантикой.
2. Сохранить `n x T` для фиксированной длины; добавить `* x T` для переменной. Записи `(T0, T1, …)` имеют фиксированную форму и допускают разные типы полей. Вложенные списки и записи допустимы.
3. Добавить выражения создания: `[4, 3, 4]`, `[]`, `(7, 9)`, `[(1, 2), (2, 3)]`. Это линейная адаптация для нашего диалекта. Пустой список требует известного типа из контекста. Скобки без запятой остаются группировкой выражения.
4. Порядок и повторы сохраняются. Равенство составных значений структурное: одинаковые длины/формы и равные соответствующие компоненты. Не добавлять неявное удаление повторов или упорядочивание контейнеров.
5. Присваивание, передача аргумента и возврат имеют семантику значения, рекурсивно по вложенным спискам и записям. Изменение копии не меняет оригинал. Это намеренное изменение нынешней семантики совместного использования CLR-массивов.
6. Сохранить компонентные пути `Z0[i0]`, `Z0[(i0 + 1)]`, `Z0[i0.1]`. Запись в существующий элемент разрешена; выход за границы не расширяет список.
7. Преобразования длины возвращают новое значение. Правая часть полностью вычисляется до замены получателя: `Lz(Z0, Z0) => Z0` удваивает прежний список.
8. Фиксированная длина обязательна. Известное несоответствие отвергается при компиляции; присваивание значения неизвестной длины в `n x T` проверяет длину при исполнении. Тип элементов должен быть совместим независимо от длины.
9. Сохранить исторические обозначения основных операций: `N`, `Lz`, `Qz`, `Sp`, `Nr`. Их написание должно поддерживаться грамматикой, которая сейчас принимает обычные имена со строчной буквы.
10. Списки — нативная возможность языка, не надстройка над ручной кучей. Не подключать к ним `@`, `NativeMemory` или освобождение пользователем. Существующее расширение динамической памяти сохраняется. Не добавлять размещение списков в ручной куче. При копировании уже допустимых записей с полями-ссылками копируются ссылки, а не объекты за ними.
11. Отношения представляются списками пар. Не вводить специальные примитивные типы «отношение», «цепь» или «кольцо». Соответствующие свойства проверяют обычные планы.
12. Не включать предложенную ранее систему пользовательских ограничений типов/предикатов. Обычные проверки типов, длины и компонентов остаются обязательными.
13. Добавить механизм стандартной библиотеки: алгоритмы, выразимые средствами языка, писать на Plankalkül, а не дублировать их в Python/C#.

## Операции и примеры согласованного поведения

| Запись | Поведение |
|---|---|
| `N(Z0)` | Длина списка |
| `Lz([1, 2], [3, 4])` | `[1, 2, 3, 4]` |
| `Qz([1, 2], [7, 8])` | `[(1, 7), (2, 8)]` |
| `Sp([(1, 7), (2, 8)], 1)` | `[7, 8]` |
| `Nr([7, 8])` | `[(0, 7), (1, 8)]` |
| `9 => Z0[2]` | Замена существующего элемента |
| `Lz(Z0, [9]) => Z0` | Добавление в конец |
| `Lz([9], Z0) => Z0` | Добавление в начало |
| `insert(Z0, 2, 9)` | Новый список со вставкой перед позицией 2 |
| `remove(Z0, 2)` | Новый список без элемента позиции 2 |
| `reverse(Z0)` | Новый список в обратном порядке |

`Lz` в нашем начальном варианте принимает списки: отдельный элемент упаковывается в `[элемент]`, чтобы не создавать неоднозначность для вложенных списков. `Qz` требует равной длины и не обрезает аргументы. Для `Sp` путь/номер поля должен быть известен при компиляции; первая версия может ограничиться одним статическим номером. Названия insert/remove/reverse — современные библиотечные имена, не заявления об историческом синтаксисе.

## Архитектура стандартной библиотеки

Ниже сохранено исходное предложение; принятый и реализованный вариант описан в конце документа и в lists.md.

Цель: поставляемые исходники `.pk` проходят тот же разбор, анализ и генерацию IL, что пользовательские планы. Пользователь вызывает стандартный план по имени. Не создавать отдельный интерпретатор библиотеки и не подменять её тела скрытым C#-алгоритмом.

Минимальные встроенные возможности: тип и хранение списка, литералы, длина, проверяемый компонентный доступ, присваивание/копирование. Для построения результата переменной длины понадобится ещё базовая операция: например, соединение списков Lz. Точная граница ядра и библиотеки требует решения перед реализацией: нельзя объявить Lz библиотечным, не предоставив ему способ создать результат нужной длины.

Предлагаемый первый срез: N и Lz обеспечиваются ядром; insert/remove/reverse/Nr реализуются стандартными планами через W1–W5, компоненты, литералы и Lz. Qz и Sp — также кандидаты на библиотечные тела, но их сигнатуры требуют работы с типами элементов и полей. При построении через многократный Lz явно учитывать стоимость копирования; не обещать линейное время без измерений или специального построителя.

До кодирования библиотеки согласовать небольшой механизм параметризации типов. Нельзя ограничить всё int32 или копировать один алгоритм вручную для каждого типа. Возможный путь — шаблонные стандартные планы с выводом типов по аргументам и специализацией при компиляции. Это предложение, не согласованный синтаксис пользовательских обобщений.

Требования к подключению:

- Отдельная внутренняя идентичность стандартных планов; их P-номера не конфликтуют с пользовательскими P0/P1. Определить разрешение совпадающих имён без молчаливой подмены.
- Подключать используемые планы и их зависимости. Не сшивать исходники простым текстовым добавлением, теряя координаты файлов.
- Ошибки библиотеки сохраняют имя её файла и позицию, вызов — позицию пользовательского исходника.
- Исходники библиотеки входят в wheel; их изменения учитываются в ключе кеша сборки.
- `parse`, `analyze`, `compile`, `build`, `run` и нотация используют согласованный механизм разрешения вызовов.
- Стандартный план должен быть доступен для просмотра в нотации. Политику подсветки/контрольных точек внутри библиотеки определить явно: позиция чужого файла не должна подсвечивать одноимённую строку пользовательского исходника.

## Исходные вопросы (решения зафиксированы ниже)

Этот список сохранён для истории проектирования. Ответы зафиксированы в разделе «Принятые решения при реализации» и в lists.md; повторное согласование не требуется.

1. Точный синтаксис параметров типов стандартных планов; будет ли он сразу доступен пользователю.
2. Минимальная операция построения списков и граница ядра/библиотеки; стартовый компромисс — встроенный Lz.
3. Вариадические Lz/Qz или первоначально два аргумента; расширенные пути Sp или одно поле.
4. Вывод фиксированной/переменной длины из литералов и результатов операций. Не допустить, чтобы переменная, впервые получившая `[1, 2]`, неожиданно стала нерасширяемой без ясного правила.
5. Инициализация вложенных структур: переменный список пуст, фиксированный содержит заданное число начальных значений; точно определить правила для записей, параметров и результатов.
6. Семантика замены компонентов входного параметра: изменение локальной копии допустимо, исходное значение вызывающего плана сохраняется. Сверить с существующими ограничениями V.
7. Числовой тип длины/индекса, предел размера платформы, диагностика нехватки ресурсов; это не лимит ручной кучи.
8. Наблюдение за библиотечными вызовами в машине без расширения задачи до полноценного отладчика.

## Приёмка без избыточных прогонов

- Разбор и типизация вложенных литералов, пустого списка, несовместимых элементов и длин.
- Независимость копий списка, вложенного списка и записи со списком; аргументы и результаты. Существующие поля-ссылки сохраняют идентичность объектов, а не глубоко клонируются.
- Структурное равенство с порядком, повторами и пустыми значениями.
- N/Lz/Qz/Sp/Nr и стандартные insert/remove/reverse: обычные случаи и пустые значения, допустимые и недопустимые позиции. Для вставки позиция N допустима; для чтения/замены/удаления — нет.
- Несовпадение длин Qz, известное и вычисляемое нарушение фиксированной длины.
- Реальное выполнение с .NET, использование стандартной библиотеки из установленного пакета вне репозитория, изменение библиотеки инвалидирует кеш.
- Регрессии существующих W/FIN, списка на @node и освобождения его объектов. Не переписывать этот пример под нативные списки: он демонстрирует другое расширение.
- Сборка WPF; UI и Computer Use не запускать. Визуальную проверку поручить пользователю.
- Проверки по затронутым участкам во время разработки; один итоговый полный прогон. Не размножать проверки форматирования IL и не гонять весь набор после каждой мелочи.
