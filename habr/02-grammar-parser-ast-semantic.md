# Plankalkül -> AST: грамматика, парсер и семантика. Часть 2

В первой части я описал цель проекта: взять программу на линейной нотации Plankalkül, разобрать ее, проверить и сгенерировать CIL для .NET. Теперь разберем середину этого пути: грамматику, parser, AST и семантический анализ.

Это та часть компилятора, где текст перестает быть просто текстом. После frontend-а у нас появляется структура программы, а после semantic analysis - понимание типов, переменных, вызовов и корректности операций.

## Почему нужна формальная грамматика

Историческая запись Plankalkül интересна сама по себе, но компилятору нужен однозначный входной язык. В проекте используется ANTLR4-грамматика `grammar/Plankalkul.g4`. Она описывает линейную текстовую нотацию, с которой дальше работает весь pipeline.

Верхний уровень простой:

```antlr
program
    : (typeDef | programDef)* EOF
    ;
```

Файл состоит из определений типов и определений программ. Например:

```text
int = 8.0

P0 max (V0[:int], V1[:int]) -> R0[:int]
  V0 => Z1
  (Z1 < V1) -> V1 => Z1
  Z1 => R0
END
```

Здесь `int = 8.0` - `typeDef`, а `P0 max (...)` - `programDef`.

## Типы

Правило типов в грамматике поддерживает битовые последовательности, массивы, records и пользовательские имена:

```antlr
typeExpr
    : INT
    | INT '.' INT
    | INT 'x' typeExpr
    | '(' typeExpr (',' typeExpr)+ ')'
    | name=ID
    ;
```

Этого хватает, чтобы записать как простой alias:

```text
int = 8.0
```

так и составные типы:

```text
A1 = (S1.8, S1.8)
A2 = 100 x A1
```

Синтаксис компактный, но для компилятора за ним стоит важная задача: позже нужно будет понять, совместимы ли два типа структурно, куда можно писать значение и как это значение представить в CIL.

## Программы и statements

Определение программы содержит идентификатор `P`, необязательное имя, список параметров, результаты и тело:

```antlr
programDef
    : programId name=ID? '(' paramList ')' '->' resultSpec
      statementList
      'END'
    ;
```

Statements в текущей грамматике покрывают базовые конструкции проекта:

```antlr
statement
    : expr '=>' varRef
    | expr '->' guardBody
    | wLoop
    | forLoop
    ;
```

Это хорошо показывает характер языка. Присваивание - это поток значения в переменную. Условное выполнение - это guard. Циклы представлены отдельно как `W` и `FOR`.

Важная деталь: `->` встречается и в сигнатуре программы, и в guard-операторе. Грамматика разводит эти случаи контекстом: в `programDef` это часть объявления результата, внутри `statement` - условное выполнение.

## Выражения

Выражения описаны через уровни приоритета:

```antlr
orExpr
    : andExpr ('|' andExpr)*
    ;

andExpr
    : compExpr ('&' compExpr)*
    ;

compExpr
    : addExpr (compOp addExpr)?
    ;

addExpr
    : mulExpr (('+' | '-') mulExpr)*
    ;
```

Так parser сразу различает, что `*` сильнее `+`, сравнения слабее арифметики, а boolean-операторы еще слабее.

Для языка это важно не меньше, чем для привычных C-like языков. Например:

```text
V0[:8.0] + V1[:8.0] * 2 => R0[:8.0]
```

должно означать `V0 + (V1 * 2)`, а не `(V0 + V1) * 2`.

## Ссылки на переменные

Одно из самых специфичных правил - `varRef`:

```antlr
varRef
    : varKind INT ('[' component? (':' typeInline)? ']')?
    ;

varKind
    : 'V' | 'Z' | 'C' | 'R'
    ;
```

Оно покрывает несколько форм:

```text
V0
V0[:8.0]
Z0[0 : A2]
Z0[Z1.1 : A2]
```

В одной конструкции здесь смешиваются:

- семейство переменной;
- номер переменной;
- опциональный путь к компоненту;
- опциональная inline-аннотация типа.

ANTLR может разобрать такую запись, но parse tree еще не является удобной моделью программы. Поэтому следующий слой - собственный AST.

## Почему не работать прямо с parse tree

ANTLR parse tree отражает грамматику. Это хорошо для parser-а, но не всегда хорошо для остального компилятора.

Например, в parse tree много технических узлов: уровни приоритета выражений, скобки, варианты правил, токены-разделители. Для семантического анализа удобнее получить более чистые сущности:

- `Program`;
- `ProgramDef`;
- `TypeDef`;
- `Assignment`;
- `GuardedStmt`;
- `WLoop`;
- `ForLoop`;
- `BinaryExpr`;
- `UnaryExpr`;
- `VarRef`.

В проекте эти узлы описаны frozen dataclass-ами в `src/plankalkulsharp/plankalkul_ast/nodes.py`. Это делает AST стабильной границей между frontend-ом и остальными слоями.

## ASTBuilder: CST -> AST

Переход от ANTLR CST к AST выполняет visitor `ASTBuilder`.

Упрощенно его роль такая:

```text
ANTLR parse tree
  |
  v
ASTBuilder visitor
  |
  v
project AST dataclasses
```

Например, assignment из исходника:

```text
V0 => Z1
```

после parser-а становится частью CST, а после `ASTBuilder` - узлом `Assignment`, где отдельно лежат expression слева и `VarRef` справа.

Для guard:

```text
(Z1 < V1) -> V1 => Z1
```

AST уже может хранить условие как `BinaryExpr`, а тело - как вложенный statement. Дальше semantic analyzer не обязан знать, как именно ANTLR назвал промежуточные правила `compExpr`, `addExpr` или `guardBody`.

## Семантический анализ

Parser отвечает на вопрос: "Текст синтаксически похож на программу?" Семантический анализ отвечает на более сильный вопрос: "Эту программу можно корректно скомпилировать?"

В проекте semantic analyzer делает несколько крупных шагов:

1. Регистрирует пользовательские типы.
2. Регистрирует сигнатуры программ.
3. Проверяет тела программ.

Разделение нужно для forward calls: программа может вызвать другую программу, и analyzer должен знать ее сигнатуру до проверки конкретного тела.

## Типы и structural typing

Plankalkül строит составные значения из простых структур: битовые последовательности, массивы, записи. Поэтому в проекте важна структурная совместимость типов.

Пример:

```text
int = 8.0

P0 id (V0[:int]) -> R0[:8.0]
  V0 => R0
END
```

`int` и `8.0` здесь должны свестись к одной resolved-структуре. Для человека это очевидно, но compiler pipeline должен сделать эту нормализацию явно.

Та же идея нужна для records и arrays. Если пользовательский тип `A2` означает `100 x A1`, то при component access analyzer должен понимать структуру `A2`, а не только имя.

## Scope для V, Z, C и R

Семейства переменных Plankalkül превращаются в правила области видимости.

`V`-переменные приходят из параметров программы. `R`-переменные описываются результатом. `Z` часто появляются при первом присваивании. `C` используются как именованные константы в рамках программы.

Например:

```text
P0 max (V0[:int], V1[:int]) -> R0[:int]
  V0 => Z1
  (Z1 < V1) -> V1 => Z1
  Z1 => R0
END
```

Когда analyzer видит `V0 => Z1`, он может вывести тип `Z1` из левой части. Когда позже встречает `Z1 < V1`, он уже знает тип `Z1` и может проверить сравнение.

## Проверки, которые не видны parser-у

Parser спокойно примет многие строки, которые не должны проходить компиляцию. Например, syntactically это может выглядеть нормально:

```text
P0 bad (V0[:8.0]) -> R0[:0]
  V0 => R0
END
```

Но семантически здесь подозрительная операция: 8-битное значение записывается в однобитный результат. Именно analyzer должен решить, совместимы ли типы.

То же касается guard-условий. Конструкция:

```text
V0[:8.0] -> V0 => R0
```

синтаксически похожа на guard, но условие guard-а должно быть boolean-like значением, а не произвольной последовательностью битов, если правила языка этого не допускают.

## Где заканчивается frontend

После semantic analysis программа еще не исполняется. Но это уже не просто текст и не parse tree. У компилятора есть:

- AST программы;
- resolved-типы;
- информация о переменных;
- сигнатуры программ;
- проверенные выражения и statements.

Это удобная точка передачи в backend. Генератору CIL уже не нужно гадать, что такое `Z0[Z1.1 : A2]`: semantic layer должен был доказать, что это корректное обращение к компоненту.
