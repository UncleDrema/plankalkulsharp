# Plankalkül: компилируем первый язык программирования в .NET. Часть 1

Когда говорят об истории языков программирования, обычно быстро вспоминают Fortran, Lisp, Algol и дальше двигаются к более знакомой ветке. Но до них был Plankalkül Конрада Цузе: язык, спроектированный в 1940-е годы, задолго до привычной нам индустрии компиляторов, IDE и стандартных библиотек.

На Хабре уже есть старая обзорная статья о Plankalkül: [Первый язык программирования](https://habr.com/ru/articles/133887/). Она хорошо подходит как историческое введение: кто такой Цузе, почему язык оказался забытым, как выглядела оригинальная запись. В этой серии я хочу зайти с другой стороны: не только рассказать о языке, а показать разработку работающего компилятора.

Цель проекта PlankalkulSharp такая:

```text
Plankalkül source -> parser -> AST -> semantic analysis -> CIL -> .NET executable
```

То есть на входе у нас текстовая программа на Plankalkül, а на выходе - IL-код для CLR, который можно собрать через .NET и запустить как обычную программу.

## Почему Plankalkül вообще интересно компилировать

В Plankalkül много решений, которые выглядят непривычно даже после знакомства с несколькими языками программирования.

Во-первых, у языка исторически была двумерная нотация. Выражение, индекс переменной, индекс компонента и тип могли записываться в разных строках одной конструкции. Это красиво как артефакт истории вычислений, но неудобно для обычного текстового parser pipeline.

Во-вторых, базовый мир языка строится вокруг одного примитива: бита. Более сложные значения описываются как последовательности битов, массивы и записи.

В-третьих, имена переменных не произвольные. В языке есть несколько семейств:

| Семейство | Смысл |
| --- | --- |
| `V` | входные значения программы |
| `Z` | промежуточные значения |
| `R` | результаты |
| `C` | константы |

Такая модель влияет не только на синтаксис, но и на устройство компилятора. Например, при генерации CIL входные `V` естественно превращаются в аргументы метода, а `Z`, `C` и `R` - в локальные переменные.

## Что именно компилирует проект

В проекте используется линейная текстовая нотация Plankalkül. Она не пытается буквально воспроизвести двумерную запись Цузе, но сохраняет важные идеи языка: семейства переменных, компонентные индексы, типовые аннотации, guards и программы `P`.

Минимальный пример из тестовых программ - максимум двух 8-битных целых:

```text
int = 8.0

P0 max (V0[:int], V1[:int]) -> R0[:int]
  V0 => Z1
  (Z1 < V1) -> V1 => Z1
  Z1 => R0
END
```

Если читать это как современный псевдокод, происходит следующее:

```text
Z1 = V0
if Z1 < V1:
    Z1 = V1
R0 = Z1
```

Но синтаксис намеренно остается ближе к Plankalkül.

`P0 max (...) -> R0[:int]` объявляет программу. Входы записаны как `V0` и `V1`, результат - как `R0`. Тип `int` выше определен как `8.0`, то есть 8-битная последовательность.

Оператор `=>` читается как "получается" или "передать значение вправо". В этой нотации результат стоит справа:

```text
V0 => Z1
```

Оператор `->` используется для условного выполнения:

```text
(Z1 < V1) -> V1 => Z1
```

Это guard: если условие истинно, выполняется тело справа.

## Типы: от бита к структурам

В документации проекта базовый тип описан как `S0`: один бит, булево значение. Для практической записи в линейной нотации используются более компактные формы.

Например:

| Запись | Смысл |
| --- | --- |
| `0` | один бит, то же семейство идей, что `S0` |
| `8.0` | последовательность из 8 бит |
| `100 x A1` | массив из 100 элементов типа `A1` |
| `(S1.8, S1.8)` | запись из двух полей |
| `A1` | пользовательский тип |

В реальных примерах это позволяет описывать уже не только числа, но и структуры данных. Например, в программе разворота связного списка используется запись-узел и массив таких узлов:

```text
A1 = (S1.8, S1.8)
A2 = 100 x A1
```

Первое поле хранит значение, второе - индекс следующего узла. Указателей в привычном смысле нет, поэтому "ссылки" моделируются целыми индексами в массиве.

## Компонентные индексы

Одна из характерных частей Plankalkül - обращение к компонентам составного значения. В линейной нотации это выглядит так:

```text
Z0[Z1.0 : A2]
Z0[Z1.1 : A2]
```

Здесь `Z0` - массив записей, `Z1` - индекс элемента, а `.0` или `.1` выбирает поле записи. Аннотация `: A2` сообщает компилятору тип всей структуры.

В программе `reverse_list.pk` это используется для построения списка:

```text
FOR Z1[:8.0] FROM 0 TO Z2[:8.0] {
  Z1[:8.0] => Z0[Z1.0 : A2]
  Z1[:8.0] + 1 => Z0[Z1.1 : A2]
}
```

Первая строка записывает значение узла, вторая - индекс следующего узла.

## Управление потоком: guards, W и FOR

Условный оператор в проектной нотации строится через guard:

```text
(condition) -> statement
```

Для блока:

```text
(condition) -> {
  statement
  statement
}
```

Цикл `W` работает как повторение набора guard-ов. Пока хотя бы один guard срабатывает, цикл продолжается. Например, итеративный Fibonacci в проекте использует такую форму:

```text
W {
  (Z2[:8.0] < V0[:8.0]) -> {
    Z0[:8.0] + Z1[:8.0] => Z3[:8.0]
    Z1[:8.0] => Z0[:8.0]
    Z3[:8.0] => Z1[:8.0]
    Z2[:8.0] + 1 => Z2[:8.0]
  }
}
```

`FOR` в проекте - практическое расширение линейной нотации. Оно делает демонстрационные программы короче и понятнее, но компилятор все равно сводит его к обычным переходам в generated IL.

## Как выглядит весь pipeline

Внутри компилятор разделен на несколько этапов:

```text
.pk source
  |
  v
ANTLR lexer/parser
  |
  v
CST -> AST
  |
  v
semantic analysis
  |
  v
CIL text assembly
  |
  v
dotnet build
  |
  v
.NET executable
```

Такое разделение важно. Если сразу генерировать IL из дерева ANTLR, проект быстро станет хрупким: синтаксические детали будут смешаны с типами, областями видимости и backend-ом. Поэтому в середине есть собственный AST и отдельный семантический анализ.

В следующих частях я разберу эти слои подробнее. Сначала - как из исторически необычной нотации получается формальная ANTLR-грамматика, собственное AST и проверенная программа. Потом - как эта программа превращается в CIL и запускается через .NET.
